# 試營運資料庫與安全計畫

這份文件界定正式試營運時的最小資料層；競賽 Demo 目前不連線資料庫。

## 儲存範圍

只保存店家、已發布優惠、優惠券狀態、核銷時間與核銷店家身分。訪客資料只用已驗證帳號的內部識別碼來綁定券，不保存祈願原文、宗教推論、精確定位或不必要的個人檔案。

## 完整性規則

- 券碼是不可預測 UUID，不採連號或可猜測的短碼。
- 每張券只會由發券 RPC 建立；每一次核銷只會由核銷 RPC 更新。
- 同一位訪客對同一優惠的重複點擊會在同一交易序列化，回傳既有可用券，不會建立重複券或產生不必要錯誤。
- 核銷 RPC 會鎖定資料列，因此同時送出的兩次核銷僅能有一次成功。
- 核銷者必須是該優惠所屬店家的已驗證成員；伺服器依 `auth.uid()` 判斷，前端不可自行指定店家。
- 優惠需在有效期間且已發布；逾期券會轉為 `expired`，不可恢復為可用。

## 權限模型

| 角色 | 可做的事 |
| --- | --- |
| 訪客 | 讀取已發布優惠、讀取自己的券、領取自己的券 |
| 店員 | 僅核銷自己店家的券 |
| 店家擁有者 | 另以受保護的後台 API 維護該店資料 |
| 平台管理員 | 透過伺服器端管理工具執行營運作業，不經 MINI App |

所有表格都開啟 Row Level Security。瀏覽器使用的僅是 Supabase URL 與 anon key；`service_role` 金鑰只能留在受管控的伺服器環境變數。

## 上線前清單

1. 建立獨立的 Supabase 專案，執行 `supabase/migrations/202608030001_secure_coupon_core.sql`。
2. 完成 LINE Login 與伺服器端 token 驗證，再建立對應的 Supabase session；不可相信瀏覽器傳來的 LINE user ID。
3. 將發券、核銷 API 的錯誤轉為通用訊息，避免洩漏其他店家或使用者的券狀態。
4. 設定 HTTPS、受限 CORS、速率限制、登入與核銷異常監測；記錄最少量的安全稽核事件。
5. 以兩個店員帳號同時核銷同一券做併發測試，確認僅一筆成功。
6. 先完成保留期限、刪除要求與資料外洩應變流程，再邀請真實使用者。

## 不可取代的伺服器責任

前端不能承擔權限判斷、一次性券碼狀態或管理者能力。競賽版的 PIN 與固定券碼只供展示，絕不可沿用到試營運。
